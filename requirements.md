# Scope, checked with Ponytail

Build a separate local app in `new mass gen` for the provided Ukrainian CSV. One CSV row becomes one educational illustration. Keep CSV order and Ukrainian filenames. Install pinned Oracle 0.21.6 and use its persistent browser-session infrastructure with Gemini's Create image tool; no paid API key is needed. The CLI image path was tested and returned text instead of an image, so the app uses the real website's image tool.

The input has 141 terms. Preserve the 26 already completed illustrations and their per-term scene ideas. The default queue therefore contains 115 unfinished terms. Use one image request at a time, save progress after each result, and pause on login, exhausted account quotas, or provider errors. A restart must not resend an uncertain request automatically.

The interface needs setup/login, source CSV import with column selection, prompt and style preview/editing, search, a number range, batches of 10/25/50/100 or all remaining, start/pause, individual retry, image previews, and a downloadable progress report. One start runs the entire selected batch without per-image actions. Store images in `output/images` with names like `27. Назва.jpg`; never overwrite an existing image. Retain request logs under the current user's application-data folder. Protect local API, log and image routes with an automatically established session. Diagnostic page screenshots are opt-in and removable from the interface.

Add a saved delay setting in seconds, defaulting to 30 for new and existing queues. Accept whole values from 0 to 3600; 0 disables waiting. Wait after each finished attempt before the next, including retries and account failover. Retain the last attempt's finish time across batches and process restarts, show the remaining wait in the UI, and let Pause or shutdown cancel waiting without sending another request. Do not delay a fresh queue's first request or the completion of a batch that has no next request.

Files reached: `core.mjs` (CSV, prompts, queue), `oracle.mjs` (browser and process), `server.mjs` (local HTTP and saved state), `public/*` (interface), `launch.mjs` and the Windows launcher (startup), `package.json` / lockfile (Oracle installation), input and scene data (initial dataset), tests and README (verification and use).

Allow selecting an existing normal Chrome profile from its profile labels. Open that profile normally, use Chrome's own remote-debugging approval flow, and attach through Oracle to a uniquely marked app-owned tab in that exact profile. Reuse that tab for fresh chats in the batch. Do not copy or decrypt credentials, relaunch the normal profile with debugging flags, change browser permissions automatically, use unrelated tabs, or close the user's Chrome. The existing-profile mode is visible Chrome and cannot be combined with headless mode. A separate connection check must not send an image prompt.

Use Node 24, its standard library, and Oracle. Reuse the existing term scene descriptions and finished images as seed data. Do not modify previous studios or their private state. Keep the server bound to localhost and reject requests from other sites.

Each existing Chrome profile has its own ordered list of named Gemini account home URLs; the hidden generator has its own ordered list of isolated account sessions. Support adding and editing names/URLs, enabling/disabling accounts, and moving them up/down. Persist changes and prevent editing while generation is active. Accept only HTTPS Gemini home URLs, preserve account paths and query parameters, and reject duplicate account slots. Before submitting a prompt, verify the destination account slot to stop silent redirection to another account.

For unattended work on the same PC, prefer headless Chrome managed through Oracle. Give each named background account its own persistent Chrome user-data directory, retaining the original main profile for compatibility. Route all background requests to the account's own session and the standard Gemini home URL; indexed /u/N URLs are only for the existing visible Chrome mode. In hidden mode, multiple accounts can use the same home URL because their sessions are isolated. Provide per-account one-time login and hidden login checks without image requests. Never automatically open a visible login window during a batch. Confirm the actual connected browser reports headless before page automation, and do not bring hidden sessions to the foreground. Add Stop now to abort the current request and retain it for review without sending the next one.

Separate human sign-in from browser automation: the manual login launcher uses normal Chrome with the saved user-data directory but no remote debugging or automation flags. Track that browser's lifetime so hidden generation cannot launch against a profile still open for manual sign-in. Never dismiss or bypass Google's insecure-browser rejection or weaken browser/account security settings. A legacy debugging-enabled login window must be closed before normal sign-in can start.

Use the first enabled account until Gemini reports a quota. Disable and mark that account, then retry the current term on the next enabled account in the saved order. Keep subsequent terms on that account. Pause after all enabled accounts reach their quotas. Re-enabling an account or adding an available one restores the quota-stopped term to pending without starting generation automatically. The user must re-enable a limited account after access returns; there is no scheduled quota reset detection. Account labels are user supplied; URL slots can change after Google sign-out or account reordering.

Skipped: hosted deployment, XLSX, multiple users, parallel generation, automatic account discovery, scheduled quota resets, and another UI framework. Gemini availability and quotas still depend on each signed-in account; live generation requires those accounts' login.

Run batches in headless Chrome by default after a one-time visible login. Reject reuse of a visible Chrome profile until it is closed. Retry capability refusals, tool setup errors and timeouts once in a fresh tab, with two total attempts per term per account per batch. Bound image waiting to 2 minutes and the full attempt to 4 minutes; bound browser commands and cleanup independently. Leave failed rows for review and continue other terms in the batch. Do not retry content refusals; login, exhausted quotas, cancellation and unclassified errors pause the batch. Show the current phase, elapsed time, account and separate saved/failed counts. A process restart does not resend an uncertain request. Preserve completed files.
